# Key Engineering Decisions

This document explains the major architectural and implementation decisions made during the development of the Store Intelligence Platform.

---

# Decision 1: Detection and Tracking Pipeline

## Options Considered

### YOLOv8 + ByteTrack

Advantages:

* Mature ecosystem
* Strong documentation
* Fast inference
* Easy OpenCV integration
* Lightweight tracking
* Stable visitor tracking across frames

Disadvantages:

* Not the highest accuracy model available
* Can struggle under severe occlusion conditions

### YOLOv8 + DeepSORT

Advantages:

* Appearance-based tracking
* Better long-term identity association

Disadvantages:

* Additional computational overhead
* More complex integration

---

## AI Recommendation

AI-assisted evaluation suggested using YOLOv8 because of its maturity, deployment simplicity, and strong community support. Multiple tracking approaches were reviewed before selecting ByteTrack.

---

## Final Choice

YOLOv8 for person detection and ByteTrack for visitor tracking.

---

## Reasoning

The detection layer required both reliable person detection and stable visitor tracking across frames.

YOLOv8 was selected because it provides a practical balance between detection accuracy, inference speed, and ease of deployment. The model integrates well with OpenCV-based pipelines and is widely used in real-world computer vision applications.

ByteTrack was selected because it is lightweight, easy to integrate, and performs well on CCTV footage where maintaining consistent visitor identities is more important than complex appearance-based re-identification.

The combination of YOLOv8 and ByteTrack enabled visitor tracking, dwell-time measurement, zone analytics, and billing-zone monitoring while keeping computational complexity low.

The focus of this project was to build a complete end-to-end analytics platform rather than optimize only for detection accuracy.

# Decision 2: Event Schema Design

## Options Considered

### Raw Detection Storage

Store only frame-level detections and bounding boxes.

Advantages:

* Maximum flexibility
* Retains all detection information

Disadvantages:

* Analytics become expensive
* Business metrics require repeated processing

---

### Session-Based Storage

Store only completed visitor sessions.

Advantages:

* Smaller storage footprint
* Simpler storage layer

Disadvantages:

* Reduced flexibility
* Difficult to extend analytics capabilities

---

### Event-Driven Architecture

Store structured behavioral events.

Advantages:

* Extensible
* Analytics-friendly
* Easy aggregation
* Supports multiple downstream consumers

Disadvantages:

* Slightly larger storage requirements

---

## AI Recommendation

AI-assisted design exploration favored an event-driven architecture because it cleanly separates detection logic from analytics logic.

---

## Final Choice

Structured event-based storage.

---

## Reasoning

The platform stores visitor activity as structured events containing:

* event_id
* store_id
* visitor_id
* event_type
* timestamp
* zone_id
* dwell_ms
* confidence

This design creates a stable contract between the detection layer and the analytics layer.

Metrics, funnel analytics, heatmaps, anomaly detection, and dashboard visualizations can all be derived from the same event stream.

The event-driven architecture also makes it easier to add future analytics without modifying the underlying detection pipeline.

---

# Decision 3: API and Storage Architecture

## Final Choice

FastAPI + SQLite

---

## Reasoning

The project required a lightweight analytics platform that could be deployed quickly and run with minimal configuration.

FastAPI was selected because it provides:

* Automatic API documentation through Swagger UI
* Strong request validation using Pydantic
* Simple development workflow
* Easy integration with Python analytics code

SQLite was selected because it provides:

* Zero configuration setup
* Lightweight deployment
* Easy local development
* Simple integration with Docker

The platform stores two primary datasets:

1. Visitor events
2. POS transaction records

Analytics endpoints query these datasets to generate:

* Metrics
* Conversion funnels
* Heatmaps
* Anomaly detection results

The FastAPI + SQLite combination allowed the entire platform to be deployed using a single Docker Compose command while keeping the architecture simple and maintainable.

# Reflection

AI tools were used throughout development to evaluate implementation approaches, review API designs, improve dashboard layouts, validate analytics logic, and explore architectural alternatives.

Suggestions generated by AI were reviewed, modified, and adapted before implementation. Final decisions were based on project requirements, deployment simplicity, observed behavior, and maintainability considerations.

The resulting architecture prioritizes:

* Simplicity
* Maintainability
* Ease of deployment
* Clear separation between event ingestion, analytics, and visualization

Future enhancements could include:

* Cross-camera re-identification
* Real-time event streaming
* Advanced anomaly detection
* Multi-store aggregation
* Interactive dashboard visualizations

while preserving the same event-driven architecture.
